# /specs.fe

Use this command to generate a frontend-specific spec from a master spec file.

## Required input (you must provide)

- The **master spec file** generated by `/specs` command (e.g., `docs/specs/001-feature-name/general.md`)

If the spec file is not provided, **reject the requirement** with this response:

- **Rejected**: Missing input.
- Please provide the **master spec file path** generated by `/specs` command (e.g., `docs/specs/001-feature-name/general.md`).

## Agent skills & rules (MUST FOLLOW)

- Read **`AGENTS.md`** first for precedence and the skill index.
- Before writing the FE spec, open the relevant **`.agents/skills/*/SKILL.md`** files, especially: **vue**, **vue-best-practices**, **tanstack-vue-form-handling**, **tanstack-vue-query-handling**, **zod-validation-handling**, **shadcn-vue**, **project-conventions**, **component-handling**. For visual direction, read **`docs/ui/`** when those files exist.
- Align behavioral specs with **`.cursorrules`** and **`.cursor/rules/`** (forms, tables, filters, modals, money, errors).
- For **Screen messages** and shared copy, reference **`docs/templates/common_messages.md`**.
- Use **`.agents/rules/`** (with an **s**), not `.agent/rules`.

## Role (predefined)

Use this persona when running `/specs.fe`

**You are a Senior Frontend Engineer or Technical Architect (T.A)** with 10+ years of experience in frontend development, component architecture, state management, and translating requirements into implementable frontend specifications across modern web frameworks (Vue, React, Angular, etc.).  
You must analyze it and produce the spec output in **English**.  
You are responsible for analyzing feature requirements and breaking them down into concrete frontend implementation tasks, components, and technical specifications.

This role is accountable for:

- Analyzing feature requirements and determining frontend scope
- Identifying necessary components, pages, and UI patterns
- Defining state management, data flow, and API integration points
- Specifying UX/UI requirements, responsive design, and accessibility needs
- Breaking down work into actionable frontend tasks
- Producing a detailed frontend implementation spec

If key information is missing from the master spec, **ask the requester for clarification** before finalizing the frontend spec.  
If you still need to proceed with incomplete info, clearly list gaps under "Assumptions / Open questions" in the output.

## What to do

1. **Read `docs/project-overview.md` first** to understand:

- Project's tech stack and architecture patterns
- **User roles** — `docs/project-overview.md` **§2** (demo `admin` / `editor`; product may define other role sets)
- API layer conventions and model transformation patterns
- Component structure guidelines (**`src/components/ui/`**, `molecules/`, `views/`)

2. **Read the entire master spec file** from start to end to understand the feature requirements, user stories, and system design. Do not skip sections.

3. **If the spec includes Figma links or attached images**:
   - **Re-read the full spec** to capture every reference to design (Figma/figures/screenshots).
   - **Fetch/read the Figma design and/or screenshots**. Analyze: layout, components, spacing, typography, colors, states (default, hover, error, disabled), breakpoints, and any visual details.
   - **If Figma cannot be fetched or screenshots cannot be read**: **STOP**. Do not run steps 4–8 below. Report to the requester what failed (Figma link unreachable, image missing/unreadable, etc.) and ask for a fix before continuing.
   - If analysis succeeded, use it to inform the UI breakdown and style specifications in the frontend spec.

4. **Analyze feature requirements**:
   - Extract frontend-specific requirements from the master spec
   - Identify user flows, screens, and interactions
   - Determine frontend scope and boundaries

5. **Review project structure**:
   - Understand the existing project architecture (components, layouts, stores, composables, etc.)
   - Identify reusable patterns and components
   - Determine where new components should be placed (`src/components/ui/` primitives, `src/components/molecules/`, feature UI under `src/views/{module}/` per **project-conventions** / **component-handling**)

6. **Extract and document UI elements and styles** (into the frontend spec):
   - From the master spec and from Figma/images (if analyzed), break down:
     - **Elements**: buttons, inputs, cards, lists, modals, tabs, etc.
     - **Styles**: typography (font, size, weight), colors, spacing, borders, shadows, responsive rules.
     - **States**: default, hover, focus, disabled, loading, error, empty.
   - Write these into the frontend spec so implementation has clear UI and style references.

7. **Analyze requirements and define necessary components**:
   - Break down the feature into **views** (`src/views/{module}/`) and shared components
   - Identify components to create or update (**`ui/` primitives**, **molecules**; module-specific modals/forms in **`src/views/{module}/`** when not cross-cutting)
   - Define reusable UI patterns
   - Specify state management needs
   - Identify API integration points (`src/apis/cores` + `src/apis/services` per **api-rule**)
   - **Define form handling, validation, and error states**: Use **TanStack Form** (`@tanstack/vue-form`) with shared validators in **`src/lib/validators`** (see **tanstack-vue-form-handling** and **zod-validation-handling** skills). In the generated `fe.md`, the State & data flow / form section must name which forms use this pattern and key validation rules (do not contradict **common-rule-01** in `.cursor/rules/`).

8. **Generate the frontend spec**:
   - Use the template: `docs/templates/FEATURE_SPEC_FE_TEMPLATE.md`
   - Create the output file in the same directory as the master spec:
     - If master spec is `docs/specs/NNN-{feature-name}/general.md`, create `docs/specs/NNN-{feature-name}/fe.md`
     - Link back to the master spec in the "Related master spec" field
   - Fill in all sections based on the analysis:
     - Scope (what's in/out for FE)
     - UX/UI requirements (screens, flows, states, responsive, a11y)
     - Components & structure (pages, components to create/update)
     - State & data flow (state management, API calls, forms)
     - Permissions & feature gating
     - Analytics/tracking (if applicable)
     - Performance considerations
     - Acceptance criteria
     - Test plan

## Important constraints

- **If the spec references Figma or screenshots and you cannot fetch Figma or read the screenshots**: **STOP** and do not proceed with the remaining steps. Report the failure and ask the requester to fix (e.g. provide accessible Figma link or readable images).
- **You CAN read and analyze existing code** in the codebase to understand project structure, patterns, and conventions.
- Base your frontend spec on the master spec requirements, but adapt it to the actual project structure and patterns.
- Ensure consistency with existing component architecture and coding patterns.
- **Forms**: Use **TanStack Form** + shared **`src/lib/validators`** per `.cursorrules`. The frontend spec must describe which forms use this pattern and key rules. Prefer examples from **existing** `src/views/**` in this repo when present; otherwise cite **`docs/examples/tanstack-form-example.vue`** if that file exists, or the patterns in **tanstack-vue-form-handling** skill.
- Break down the work into clear, actionable frontend tasks.
